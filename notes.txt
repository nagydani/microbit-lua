* BLE #bluetooth
** grammar
ATT = Attribute Protocol, the wire protocol for accessing attributes.
 - Read, Write, Notify, Indicate
 - "Send this payload to characteristic handle 0x0018."

GATT = Generic Attribute Profile, a schema: the data model and conventions built on top of ATT.
 - Services, Characteristics, Descriptors
 - "Characteristic 0x0018 is the TX endpoint of my stream."
** reliability
*** Link Layer: Reliable
- the controller retransmits automatically,
- it continues until the connection is lost or supervision timeout expires.
*** ATT/GATT: Reliable
The BLE stack guarantees delivery to the ATT layer.
When write() returns successfully, the remote GATT server has accepted the write.

So if the connection stays alive, the notification will either:

 - arrive, or
 - the connection will fail.

It won't silently disappear because of RF interference.
*** app layer
BLE cannot guarantee:

 - the application had room in its queue,
 - the application processed it,
 - the application didn't crash immediately afterward.
*** #flow control
When you call e.g. sd_ble_gatts_hvx(...), one of two things happens:

 - the stack accepts the notification into its transmit queue;
 - or it immediately returns NRF_ERROR_RESOURCES because the queue is full.

The application must then:

- stop sending,
- wait for a "TX complete" event
  - (? BLE_GATTS_EVT_HVN_TX_COMPLETE, meaning: space freed up for more messages)
- resume.


The concept is standardized, but the API isn't.

Every BLE stack has an equivalent:

Nordic SoftDevice: BLE_GATTS_EVT_HVN_TX_COMPLETE
Zephyr: notification completion callbacks or buffer availability
NimBLE: transmit-complete callbacks
BlueZ: asynchronous completion of GATT operations

The names differ, but the mechanism is the same: the local stack tells your application when its transmit resources have been freed.
** #MTU: the ATT #MTU is the hard limit
there are two different MTUs in play:

 - Link Layer PDU size — the maximum radio packet size: fragmentation is automatic.
 - ATT MTU — the maximum size of a single GATT operation: hard limit

*** python side for testing the echo service
#!/usr/bin/env python3

import asyncio
from bleak import BleakClient, BleakScanner

UART_SERVICE_UUID = "6E400001-B5A3-F393-E0A9-E50E24DCCA9E"
UART_RX_UUID      = "6E400003-B5A3-F393-E0A9-E50E24DCCA9E"
UART_TX_UUID      = "6E400002-B5A3-F393-E0A9-E50E24DCCA9E"

BLE_MAX_CHUNK_SIZE = 20  # safe BLE payload size

def ble_rx_handler(sender, data):
    text = data.decode(errors="ignore")
    print(f"\r[micro:bit] {text}\n", end="", flush=True)


async def stdin_loop(client):
    loop = asyncio.get_running_loop()

    while True:
        msg = await loop.run_in_executor(None, input, "> ")
        data = msg.encode() + b"\n"

        # chunk the message
        for i in range(0, len(data), BLE_MAX_CHUNK_SIZE):
            chunk = data[i:i + BLE_MAX_CHUNK_SIZE]
            await client.write_gatt_char(UART_RX_UUID, chunk)


async def main():
    print("Scanning for micro:bit...")

    devices = await BleakScanner.discover()

    micorbit = None
    for d in devices:
        # print(f"[device] {d}\n")
        if d.name and "micro:bit" in d.name.lower():
            micorbit = d
            break

    if not micorbit:
        print("No micro:bit found")
        return

    print(f"Connecting to {micorbit.name} ({micorbit.address})")

    async with BleakClient(micorbit.address) as ble:
        print("Connected")

        # subscribe to notifications
        await ble.start_notify(UART_TX_UUID, ble_rx_handler)

        print("Ready, printing incoming messages as they arrive.\n")

        # run stdin loop concurrently with BLE
        await stdin_loop(ble)


if __name__ == "__main__":
    asyncio.run(main())
