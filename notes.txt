* BLE #bluetooth
** grammar
ATT = Attribute Protocol, the wire protocol for accessing attributes.
 - Read, Write, Notify, Indicate
 - "Send this payload to characteristic handle 0x0018."

GATT = Generic Attribute Profile, a schema: the data model and conventions built on top of ATT.
 - Services, Characteristics, Descriptors
 - "Characteristic 0x0018 is the TX endpoint of my stream."
** reliability
*** Link Layer: Reliable
- the controller retransmits automatically,
- it continues until the connection is lost or supervision timeout expires.
*** ATT/GATT: Reliable
The BLE stack guarantees delivery to the ATT layer.
When write() returns successfully, the remote GATT server has accepted the write.

So if the connection stays alive, the notification will either:

 - arrive, or
 - the connection will fail.

It won't silently disappear because of RF interference.
*** app layer
BLE cannot guarantee:

 - the application had room in its queue,
 - the application processed it,
 - the application didn't crash immediately afterward.
*** #flow control
When you call e.g. sd_ble_gatts_hvx(...), one of two things happens:

 - the stack accepts the notification into its transmit queue;
 - or it immediately returns NRF_ERROR_RESOURCES because the queue is full.

The application must then:

- stop sending,
- wait for a "TX complete" event
  - (? BLE_GATTS_EVT_HVN_TX_COMPLETE, meaning: space freed up for more messages)
- resume.


The concept is standardized, but the API isn't.

Every BLE stack has an equivalent:

Nordic SoftDevice: BLE_GATTS_EVT_HVN_TX_COMPLETE
Zephyr: notification completion callbacks or buffer availability
NimBLE: transmit-complete callbacks
BlueZ: asynchronous completion of GATT operations

The names differ, but the mechanism is the same: the local stack tells your application when its transmit resources have been freed.
** #MTU: the ATT #MTU is the hard limit
there are two different MTUs in play:

 - Link Layer PDU size — the maximum radio packet size: fragmentation is automatic.
 - ATT MTU — the maximum size of a single GATT operation: hard limit

*** python side for testing the echo service
#!/usr/bin/env python3

import asyncio
from bleak import BleakClient, BleakScanner

UART_SERVICE_UUID = "6E400001-B5A3-F393-E0A9-E50E24DCCA9E"
UART_RX_UUID      = "6E400003-B5A3-F393-E0A9-E50E24DCCA9E"
UART_TX_UUID      = "6E400002-B5A3-F393-E0A9-E50E24DCCA9E"

BLE_MAX_CHUNK_SIZE = 20  # safe BLE payload size

def ble_rx_handler(sender, data):
    text = data.decode(errors="ignore")
    print(f"\r[micro:bit] {text}\n", end="", flush=True)


async def stdin_loop(client):
    loop = asyncio.get_running_loop()

    while True:
        msg = await loop.run_in_executor(None, input, "> ")
        data = msg.encode() + b"\n"

        # chunk the message
        for i in range(0, len(data), BLE_MAX_CHUNK_SIZE):
            chunk = data[i:i + BLE_MAX_CHUNK_SIZE]
            await client.write_gatt_char(UART_RX_UUID, chunk)


async def main():
    print("Scanning for micro:bit...")

    devices = await BleakScanner.discover()

    micorbit = None
    for d in devices:
        # print(f"[device] {d}\n")
        if d.name and "micro:bit" in d.name.lower():
            micorbit = d
            break

    if not micorbit:
        print("No micro:bit found")
        return

    print(f"Connecting to {micorbit.name} ({micorbit.address})")

    async with BleakClient(micorbit.address) as ble:
        print("Connected")

        # subscribe to notifications
        await ble.start_notify(UART_TX_UUID, ble_rx_handler)

        print("Ready, printing incoming messages as they arrive.\n")

        # run stdin loop concurrently with BLE
        await stdin_loop(ble)


if __name__ == "__main__":
    asyncio.run(main())
* stack diagnostics #debugging #stack #repl
** fiber stacks: paging vs per-fiber (2026-08-04) #model
This nrf52 port is a STACK-PAGING scheduler, not per-fiber stacks:
 - ONE shared physical execution stack at top of RAM: [__StackLimit, __StackTop)
   = [0x2001f800, 0x20020000) -- the linker `.stack` region, __StackSize = 0x800
   = 2048 bytes. every fiber runs on it.
 - each Fiber's heap buffer (stack_bottom/stack_top, grown by verify_stack_size)
   is only cold STORAGE for the stack contents while the fiber is idle.
 - on context switch, swap_context MEMCPYs the outgoing fiber's live frames down
   into its buffer (store_stack), then copies the incoming fiber's buffer back up
   onto the shared region (restore_stack). see libraries/codal-nrf52/asm/CortexContextSwitch.s:46-155.
=> single-address-range stack guard is the CORRECT model for this port.
live stack floor = __StackTop - __StackSize = where the heap ends.
if any fiber's run-to-yield quantum pushes live stack below that floor, it
collides with the (100% full) heap -> panic 020/030 / freeze / RX corruption.
verify_stack_size resizes the storage buffer, NOT the shared region, so it cannot
rescue an in-flight overrun during one quantum.

generic CODAL (other devices) assumes growable PER-FIBER stacks: each fiber's SP
lives in its own malloc'd buffer; verify_stack_size grows it. the nrf52 asm
deviates by paging everything through one top-of-RAM region.

** stack guard (vs per-fiber stack) #concept
a stack guard is DETECTION, not allocation. canary word (STACK_GUARD_MAGIC
0x5AFEC001) stamped at the stack-region bottom (stack_limit()); checked on
every context switch in codal::schedule:
 - canary check: word at stack_limit() still == magic?
 - SP check (verify_stack_size): get_current_sp() < stack_limit() -> panic
panics with DEVICE_STACK_OVERFLOW = 45 on first hit. converts silent heap
corruption into a deterministic code. does NOT fix overflow.
device has no MPU, so content canaries can't catch pure no-write SP jumps; but
recursion writes contiguously, so the bottom canary is reliable for this case.

** source of truth: linker, not #define (2026-08-04) #refactor
DEVICE_STACK_SIZE / DEVICE_STACK_BASE duplicated what the linker already encodes
(__StackSize, __StackTop) and could drift -> the very corruption the guard
catches. now:
 - codal-microbit-v2 fork commit 8181c8a (amended 896458f): hard assignment
   __StackLimit = ORIGIN(RAM) + LENGTH(RAM) - __StackSize   # top-of-RAM minus stack
 - codal-nrf52 codal_target_hal_base.cpp: stack_limit() = &__StackLimit
 - codal-core codal_target_hal.h: declare stack_limit()
 - codal-core CodalFiber.cpp: weak default
   stack_limit() = fiber_initial_stack_base() - DEVICE_STACK_SIZE
   (keeps other CODAL ports working); guard sites use stack_limit()
 - codal-core CodalHeapAllocator.cpp: heap end = stack_limit()
naming: stack_limit() (no "fiber" -- it's the shared-region floor); it was added
earlier in this session as fiber_stack_limit, then renamed to stack_limit
(2026-08-04). kept upstream
fiber_initial_stack_base() untouched (HAL contract other CODAL ports implement).
verified disasm: stack_limit() returns 0x2001f800 from the linker.
nrf52833 no longer uses DEVICE_STACK_SIZE/DEVICE_STACK_BASE for guard/heap math;
DEVICE_STACK_SIZE stays defined as the other-ports fallback.

** cleanup candidate: orphaned startup .stack (2026-08-04) #mess -> DONE 2026-08-04
build links TWO startup files: nrfx/mdk/gcc_startup_nrf52.S AND
nrfx_mods/mdk/gcc_startup_nrf52833.S. both declare .section .stack with
__StackLimit/__StackTop over Stack_Size = __STACK_SIZE (=8192) bytes. BUT
nrf52833-softdevice.ld's .stack output section has NO *(.stack) input pattern
(only ". += __stack_size" = 0x800), so those input sections are ORPHANS placed
at VMA 0 (readelf section 24, PROGBITS, 0x2000). their __StackLimit symbol
resolves to 0 -> do NOT read &__StackLimit.
the FUNCTIONAL stack is the linker-script .stack (NOBITS @0x2001f800, 0x800):
__StackTop/__stack = 0x20020000. real device stack = 2048 bytes, matching
DEVICE_STACK_SIZE. the startup Stack_Size=8192 is currently INERT; to actually
get an 8KB stack you'd need the .ld .stack and .heap to match. cleanup: decide
the single authoritative startup + reconcile Stack_Size vs __stack_size.

RESOLVED: /DISCARD/ : { *(.stack*) } drops the orphan startup .stack in BOTH 52833
ld files, so its __StackLimit/__StackTop labels no longer shadow. all stack-size
.ld work (rename __stack_size -> __StackSize, DISCARD, hard __StackLimit) now
lives in the codal-microbit-v2 fork commit 8181c8a (amended from 896458f,
2026-08-04) and is DELIVERED to the build via the submodule worktree, NOT the

** root cause (2026-08-04) -- CORRECTED
paging model (see above): every fiber (incl. each lua_event_handler_fiber running
lua_pcall) runs on ONE shared stack region [__StackLimit, __StackTop) and the
live stack grows down toward the heap floor __StackLimit = __StackTop - 2048.
deep lua_pcall recursion within a single run-to-yield quantum pushing past
__StackLimit collides with the 100% full heap -> layout/timing-dependent
corruption (020/030/freeze/RX). collectgarbage tuning pinned memory, so not
simple Lua retention.

CODAL lets the stack legitimately grow past nominal DEVICE_STACK_SIZE into free
heap as long as it doesn't reach live heap, hence stack-guard is opt-out.
